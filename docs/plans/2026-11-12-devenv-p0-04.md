# devenv P0-04: 승인 인스턴스 생명주기와 무효화

- 마스터 계획: `docs/plans/2026-11-11-devenv-evolution-master.md`
- 선행 작업: P0-01~03 (bc9a326, ceaed89, e4363f5 · LOCALLY_VERIFIED / CI_PENDING)
- 사용자 승인 사항:
  - 코드 구현과 격리 테스트
  - 신규 모듈 `hooks/approvals.py`
  - v1 승인 기록은 이관하지 않음
  - 승인된 계획 문서를 git으로 추적
  - 보안 조건 S1~S4 및 보완 A~C
- **운영 승인 저장소의 v2 활성화는 승인 범위 밖입니다.**

## 목표
승인 권한은 신뢰 저장소에 있는 ACTIVE 승인 인스턴스에서만 나온다. 다음 경우에는 과거 권한이 되살아나지 않는다.
- 계획 status 복원
- 같은 본문으로 재승인
- 저장소 스냅샷 복원
- 코드를 v1으로 롤백
- 저장소 손상

정상적인 진행 갱신(체크박스, 진행 기록)으로는 권한을 잃지 않는다.

## 보안 조건
- **S1** 저장소 잠금이나 기록이 실패하면 승인 발급과 쓰기를 모두 차단한다. 임시 권한은 없다.
- **S2** HMAC만으로는 스냅샷 롤백을 막을 수 없다. 롤백을 탐지하고, v1 코드로 롤백해도 과거 승인이 재활성화되지 않게 한다.
- **S3** 계획에서 권한을 결정하는 핵심 항목과 바뀌어도 되는 항목을 분리한다.
- **S4** 저장소가 손상되면 모든 권한을 차단한다. 복구 과정에서 권한을 자동 발급하지 않는다.
- **A** lease를 쓰지 않는다. 보호 대상 쓰기 직전마다 저장소 최신 상태를 검증한다.
- **B** 초기화와 키 교체는 신뢰할 수 있는 관리자 경로에서 사용자 확인을 받은 경우에만 가능하다. 프롬프트 문구로는 불가능하다.
- **C** 권한과 관련된 값은 frontmatter에 있더라도 모두 해시에 넣는다.

## 설계

### 0. 개발 격리와 휴면(dormant) 상태
- live hook은 `C:/Users/user/.claude/hooks/`를 직접 실행한다.
  - 그래서 개발은 scratchpad의 git worktree(branch `p0-04`)에서만 한다.
  - main에는 검증이 끝난 뒤 fast-forward로만 반영한다.
- v2 경로는 `APPROVALS_HOME/v2-active` 표식 파일이 있을 때만 동작한다.

### 1. 승인 인스턴스
- 모든 필드에 HMAC을 건다. payload에는 `v=2`, `kind`를 포함한다.
- 필드:
  - approval_id: os.urandom 16B
  - task_id
  - git_root: normcase 적용
  - plan_path: root 기준 상대경로, 미정이면 null
  - core_hash
  - scope[]
  - issued_at, expires_at: 30일
  - state(ACTIVE | REVOKED | EXPIRED), state_reason, state_at
  - supersedes, superseded_by
  - session_id, prompt_id
- 상태 전이는 ACTIVE → REVOKED | EXPIRED 한 방향뿐이다. 다른 전이는 `transition()`이 예외를 낸다.
- 재개할 때는 항상 ExitPlanMode로 새 id를 발급한다. 같은 task+root에 있던 기존 ACTIVE는 REVOKED(superseded)로 바꾼다.
- **저장소에 없는 승인은 권한이 0이다.**
- plan_path를 정하는 방법:
  - ExitPlanMode 결과의 filePath가 root 안에 있으면 그것을 쓴다.
  - 아니면 root/docs/plans에서 task와 core_hash가 일치하는 파일이 **정확히 1개**일 때 그것으로 정한다.
  - 한 번 정한 뒤에는 바꿀 수 없다.

### 2. core_hash (S3, C)
- **해시에 포함**:
  - frontmatter의 `status`를 제외한 모든 키(task 포함)
  - 제목과 모든 섹션 본문(변경 범위, 보안 조건, 설계, 검증 포함)
  - 단계 문구
- **해시에서 제외**:
  - `status` 줄(생명주기 필드로 따로 판정)
  - 체크박스 상태(`[x]`를 `[ ]`로 정규화)
  - `## 진행 기록` / `## Progress` 섹션
  - CRLF, 줄 끝 공백
- 권한 판정은 체크박스에 의존하지 않는다. 미체크 0개 요건은 v2에서 제거한다.
- 관측 결과에 따른 폐기:
  - status가 in-progress가 아닌 것을 관측하면 REVOKED(plan_status:<값>)
  - core_hash 불일치를 관측하면 REVOKED(plan_changed)
  - 파일이 없어진 것을 관측하면 REVOKED(plan_missing)
  - 한 번 폐기된 승인은 원래 상태로 되돌려도 부활하지 않는다.
- 범위는 계획 파일이 아니라 승인 레코드의 scope를 쓴다.

### 3. 쓰기 직전 판정 (A)
- 적용 시점: Edit/Write/MultiEdit pre, Stop의 범위 판정
- 세션 상태에는 approval_id 포인터만 둔다.
- 매번 저장소를 다시 읽고 다음을 검증한다.
  - 저장소 MAC, gen ≥ 증인값
  - 레코드 MAC
  - state가 ACTIVE이고 만료 전
  - task_id, git_root 일치
  - plan_path 파일을 실제로 읽었을 때 in-progress이고 core_hash 일치
  - 경로가 scope 안
- 결과:
  - 포인터가 있는데 검증에 실패하면, 보호 대상 쓰기를 승인 무효 사유와 함께 deny한다.
  - 저장소 읽기나 검증에 실패하면(손상, 롤백) 보호 대상 쓰기를 전부 deny한다.
- 남는 한계(보고에 명시):
  - 판정과 실제 쓰기 사이의 경쟁(ms 단위)
  - Bash, PowerShell, 스크립트 쓰기는 사전 판정을 하지 않는다(P0-07). Stop에서 사후로 판정한다.

### 4. 저장소와 실패 처리 (S1)
- `approvals.v2.json` = {v, gen, records, mac}
- 잠금 파일 `approvals.v2.lock`:
  - O_CREAT|O_EXCL로 만들고 pid와 시각을 기록한다.
  - 짧은 재시도에 jitter를 더하고, 총 대기 상한은 prior 2s다.
  - 10s보다 오래된 잠금은 회수한다.
- 기록 순서: 임시 파일 → fsync → os.replace. gen은 단조 증가한다.
- 실패 시 동작:
  - 발급 실패: 승인 없음, 쓰기 차단, Stop에서 보고
  - 폐기 기록 실패: 이 세션은 즉시 권한 0이 되고, 다음 훅에서 재시도한다.
    - 보고는 **"전역 취소 미완료"**로 하며 완료로 보고하지 않는다.
    - 다른 세션이 status, 해시, 파일 기준으로 내리는 폐기 판정은 저장소와 관계없이 각자 실시간으로 이루어진다.
    - 저장소에만 있는 폐기(revoke, superseded)는 영구 저장되기 전까지 다른 세션에 반영되지 않는다. 이 사실을 보고에 명시한다.

### 5. 롤백 방어 (S2)
- 고수위 증인: 서명된 {gen}을 다음 위치에 남긴다.
  - W1: `APPROVALS_HOME/hwm`
  - W2: `CLAUDE_DISCIPLINE_WITNESS` 또는 `%LOCALAPPDATA%/claude-discipline/hwm`
  - W3: 세션 상태의 seen_gen
- 쓰는 순서는 저장소가 먼저, 증인이 나중이다.
- 롤백 판정: 다음 중 하나면 ROLLBACK이며, 손상과 같게 처리한다.
  - 저장소 gen < max(증인)
  - 증인이 있는데 저장소가 없음
- 한계: 같은 사용자 권한으로 저장소와 모든 증인을 함께 되돌리면 탐지할 수 없다. 완전히 격리하려면 별도 주체가 운영하는 broker가 필요하다(P0-08b).
- v1 롤백 차단: activate가 v1 `approvals.json`을 `approvals.v1.retired-<ts>`로 옮기고 HMAC 키를 교체한다.
  - 이후 v1 코드로 돌아가도 기존 레코드는 서명 검증에 실패한다.

### 6. 관리자 경로 (B)
- 실행: `python -I hooks/approvals.py activate|reset --home <dir> [--witness <path>]`
- 동작 조건:
  - stdin과 stdout이 모두 대화형 TTY여야 한다.
  - 사용자가 화면에 표시된 일회용 확인 코드를 입력해야 한다.
- 위 조건을 만족하지 않으면 거부하고 아무것도 바꾸지 않는다.
  - Claude 도구의 셸, 중계 메시지, 프롬프트 문구로는 실행할 수 없다(stdin이 null이므로).
- `reset`:
  - 손상된 파일은 `.corrupt-<ts>`로 격리한다.
  - 키를 교체한다.
  - gen = max(증인)+1, 레코드 0개로 시작한다.
  - **권한을 발급하지 않는다.** 이후 계획마다 ExitPlanMode 재승인이 필요하다.
- `activate`: v1을 퇴역시키고, 키를 교체하고, 빈 v2 저장소와 `v2-active` 표식을 만든다.
- 이번 단계에서는 합성 저장소와 테스트 키로만 실행한다.
