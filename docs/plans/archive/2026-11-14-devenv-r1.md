## Context
subagent(예: code-reviewer)의 결과 보고는 UserPromptSubmit으로 도착한다. 지금 hook은 이런 중계 메시지를 받으면 승인을 무조건 버린다(`hooks/discipline.py:1685-1688`). 그래서 리뷰를 한 번 돌릴 때마다 사용자가 `task:<id>`를 다시 입력해야 작업이 이어진다. 이 세션에서도 매번 그랬다.

v1에서는 세션 상태에 저장된 승인 자체가 권한이었으므로 버리는 것이 맞았다. v2에서는 세션이 승인 번호(포인터)만 들고 있고, 보호 대상 쓰기마다 저장소와 계획 파일을 다시 검증한다(`v2_write_check`, `discipline.py:1401`). 따라서 포인터를 유지해도 취소·만료·계획 변경은 그대로 막힌다. 이제 안전하게 풀 수 있다.

목표: **이 세션이 직접 띄운 subagent의 결과 보고**가 도착했을 때만 승인 포인터를 유지한다. 그 밖의 중계 메시지는 지금처럼 승인을 버린다.

## 확인한 사실
- 중계 처리: `on_prompt`(`discipline.py:1672`)가 `relay_shaped`(1657)로 판정하고, 중계면 `state["approval"] = None`, 경고 `RELAY_NOTE`를 넣는다. 파일 수 집계와 기준선은 유지한다.
- 이 세션 트랜스크립트의 중계 메시지 형식(2건, 둘 다 code-reviewer 결과):
  - 첫 줄 `Another Claude session sent a message:`, 다음 줄 `<agent-message from="<agent id>">`.
  - 다른 형식(`<task-notification>` 등)으로 온 subagent 결과는 이 세션에 없었다.
- F4b가 SubagentStart 때 `state["agents"]`에 `<agent_type>:<agent_id>` 라벨을 기록한다(`on_agent_start`, 560행). 이 기록은 hook 이벤트에서 오므로 프롬프트 글자로 만들 수 없다.
- `from` 값과 SubagentStart의 `agent_id`가 같은 값인지는 미확인이다. 저장소 폴더가 읽기 차단이라 상태를 직접 볼 수 없다. 구현 뒤 실제 code-reviewer 실행으로 확인한다(6단계).
- 승인은 프롬프트에 묶인다: `active_approval`(1071행)은 포인터의 `prompt_id`가 현재 프롬프트와 같을 때만 인정한다. 유지하려면 중계 프롬프트의 id로 다시 묶어야 한다.
- 기존 테스트(`tests/test_approvals.py`): v1 R1~R9(508행~), v2 "relay drops the pointer"와 R7(949행~). 이들이 쓰는 중계 메시지는 기록되지 않은 agent(`from="x"`)이거나 `<task-notification>`이므로, 아래 설계에서도 기대값이 그대로다.

## 설계
`on_prompt`의 중계 분기만 바꾼다. 아래 조건을 **모두** 만족하면 포인터를 유지하고, 하나라도 어긋나면 지금과 똑같이 버린다(`RELAY_NOTE`).

1. v2가 활성 상태다(`v2_active()`). v1 경로는 바꾸지 않는다.
2. 중계 전 상태에 v2 포인터(`v == 2`, `approval_id`)가 있다. 없던 승인은 생기지 않는다.
3. 메시지가 `Another Claude session sent a message:` 다음 줄에 `<agent-message from="ID">`를 가진 형식이고, `ID`가 이 세션의 `state["agents"]`에 기록된 agent의 id와 정확히 같다.
4. 현재 cwd의 git root가 포인터의 `base`와 같다.
5. 지금 검증이 통과한다: 기존 `v2_write_check`를 그대로 호출한다(저장소 신뢰, ACTIVE, 계획 해시, 만료, 폐기 대기). 실패하면 그 사유를 경고로 남기고 버린다.

유지할 때 하는 일: 포인터의 `prompt_id`를 중계 프롬프트의 id로 바꾸고, 경고는 비운다. 권한 범위(scope)는 저장소 값을 그대로 쓴다. 이후 쓰기마다 `v2_write_check`가 계속 다시 검증한다(변경 없음).

새 코드는 순수 함수 하나(`relay_agent_id(prompt) -> str | None`)와 판정 함수 하나(`v2_keep_on_relay(...)`)로 두고, 정의를 호출부보다 먼저 둔다. 예외는 hook 경계에서 잡아 "버림"으로 처리한다(실패 시 닫힘).

### 검토한 대안
| 방식 | 판단 |
|---|---|
| A. 기록된 내 subagent의 보고일 때만 유지 | **채택** |
| B. 모든 중계 메시지에서 유지 | 기각: 다른 세션이 보낸 메시지가 끝난 턴의 승인을 이어받는다 |
| C. 지금처럼 항상 버림 | 기각: 리뷰마다 사용자가 재입력해야 한다(현재 문제) |

### 남는 위험
- 첫 줄과 `from` 줄은 글자일 뿐이다. 기록된 agent id를 아는 주체가 같은 형식을 흉내 내면 포인터가 유지된다. 유지되는 것은 사용자가 이미 승인한 같은 계획·같은 범위뿐이고, 쓰기마다 재검증된다. 새 승인이나 범위 확대는 불가능하다.
- 사용자가 직접 같은 형식을 입력해도 유지된다(사용자 본인의 입력이므로 허용).
- background subagent나 재개된 subagent의 보고 형식이 다르면 유지되지 않고 지금처럼 동작한다(안전한 쪽).
