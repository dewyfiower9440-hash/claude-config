## Context
한 턴(사용자 입력 한 번) 안에서 작업 A를 끝내고 작업 B의 계획을 승인받아 이어서 하면, 턴이 끝날 때 Stop hook이 A에서 정상적으로 고친 파일들을 "B의 변경 범위 밖"이라고 보고한다. P0 진행 중 작업을 넘길 때마다 이 보고가 나왔고, 그때마다 사실을 설명하고 넘어갔다. 거짓 보고가 반복되면 진짜 범위 위반 보고도 가볍게 넘기게 된다.

## 확인한 사실
- Stop의 범위 판정 `_scope_decision`(`hooks/discipline.py:2699-2720`)은 "이번 턴에 바뀐 파일 전부"(`state["turn_changes"]`)를 "지금 승인"의 범위와 비교한다. 턴 도중 승인이 바뀐 것을 모른다.
- 턴의 기준 내용은 프롬프트가 올 때 저장소별로 잡는다(`refresh_turn_baselines`, `:2253`). Stop 때 `refresh_content`가 현재 내용과 비교해 `turn_changes`를 만든다(`:2400-2425`).
- 새 승인은 ExitPlanMode의 PostToolUse에서 기록된다(`on_post`, `:885-887` → `record_approval` / v2는 `v2_record_approval`). 이때 이전 승인 포인터가 새 것으로 바뀐다.
- 승인이 지금 유효한지는 `active_approval`(이번 프롬프트의 승인인가)과 v2의 `v2_write_check`(저장소의 기록이 ACTIVE인가, 계획이 바뀌지 않았나)로 판정한다.

## 설계
### 승인이 바뀌는 순간에, 직전 승인이 덮던 변경을 적어 둔다
- ExitPlanMode의 post에서 새 승인을 기록하기 **전에** `keep_covered_changes`를 부른다:
  1. 직전 승인이 이번 프롬프트의 것이고(`active_approval`), v2라면 지금도 유효할 때만(`v2_write_check`가 거부하지 않음) 진행한다. 아니면 아무것도 적지 않는다.
  2. 저장소별로 턴 기준과 현재 내용을 비교해 바뀐 파일을 구한다(`worktree.content_map`, `worktree.changed` — Stop과 같은 함수).
  3. 그중 **직전 승인의 범위 안**인 파일만 `state["turn_covered"][경로] = 지금의 내용 해시`로 적는다(지워진 파일은 빈 값).
- Stop의 `refresh_content`는 `turn_changes`를 만들 때, 적힌 해시와 **현재 내용 해시가 같은** 파일을 뺀다. 승인이 바뀐 뒤 다시 고친 파일은 해시가 달라져 빠지지 않는다.
- `turn_covered`는 새 프롬프트가 올 때 비운다(턴 기준을 새로 잡는 곳).

### 바뀌지 않는 것
- 직전 승인이 없었거나, 무효였거나, 그 범위 밖이었던 변경은 지금처럼 보고된다.
- git 조회가 시간 안에 안 되면 아무것도 적지 않는다(지금과 같은 보고가 나온다).
- 쓰기 전 판정(pre), 승인 발급·폐기 규칙, 내용 검증(게이트 증거)은 건드리지 않는다. 범위에서 빠진 파일도 "검증 안 됨" 판정은 그대로 받는다.

### 검토한 대안
| 방식 | 판단 |
|---|---|
| A. 전환 순간에 덮인 변경을 내용 해시와 함께 기록 | **채택**: 전환 뒤의 재수정을 구분할 수 있다 |
| B. 전환 순간에 턴 기준을 새로 잡는다 | 기각: 승인 없이 한 변경과 범위 밖 변경까지 기준 뒤로 사라진다 |
| C. Stop에서 "이번 턴에 유효했던 승인들의 범위 합집합"과 비교 | 기각: 어느 변경이 어느 승인 아래에서 일어났는지 구분하지 못해, 뒤 승인의 범위로 앞의 무승인 변경을 가릴 수 있다 |
