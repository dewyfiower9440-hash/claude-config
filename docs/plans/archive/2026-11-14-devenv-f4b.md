- 마스터 계획: `docs/plans/2026-11-11-devenv-evolution-master.md` (재정렬 순서 4번째)

## Context
F4a로 세션 상태에 "누가 남긴 기록인지"는 적히게 됐다. 그러나 subagent가 언제 시작하고 끝났는지는 hook이 모른다. 그래서 두 가지가 남아 있다.

1. 사라진 저장소 경고에 subagent 이름이 나와도, 그 subagent가 이미 끝났는지(저장소가 돌아올 가능성이 없는지) 알 수 없다. 사용자가 `ack-missing`을 판단할 근거가 부족하다.
2. 원인 자체(리뷰 subagent가 추적되는 위치에 재현용 저장소를 만들고 지움, `p3parent` 사례)를 막는 장치가 없다. subagent는 자기 도구 호출이 메인 세션의 추적 상태에 기록된다는 사실을 모른다.

마스터플랜의 F4b 정의는 "SubagentStart/Stop 등록"뿐이고 설계와 수용 기준이 없다. 이 계획이 정한다.

## 확인한 사실
- 공식 문서(code.claude.com/docs/en/hooks, 2026-11-14 조회):
  - SubagentStart 입력: 공통 필드 + `agent_id`, `agent_type`. **subagent 생성을 막을 수 없다.** `hookSpecificOutput.additionalContext`로 subagent 대화 시작 부분에 문맥을 넣을 수 있다. Agent 도구로 만들 때, 재개할 때, in-process teammate가 새 메시지를 처리할 때마다 실행된다.
  - SubagentStop 입력: 위에 더해 `stop_hook_active`, `agent_transcript_path`, `last_assistant_message`. `decision: "block"`이나 exit 2는 subagent를 계속 돌게 한다. 내부 agent(프롬프트 제안, `/btw`)에서도 실행되며 그때 `agent_type`은 빈 문자열일 수 있다.
  - 두 이벤트 모두 matcher는 agent type에 맞춘다.
  - 문서에 없는 것(미확인): background subagent에서의 실행 여부, 재개된 subagent의 SubagentStop, 이벤트의 `session_id`가 부모와 같은지(예시는 같게 나옴), SubagentStart가 subagent 시작 전에 끝나는지.
- `hooks/discipline.py`
  - `main()`(2431행 부근)은 모드 표에 없는 모드를 exit 0으로 넘긴다. 새 모드는 표에 추가해야 동작한다.
  - `blocks(mode, data)`는 `pre`와 `stop`만 참이다. 새 모드는 실패해도 차단 출력을 내지 않는다.
  - `run_hook`은 잠금 실패나 예외 때 `note_safely`로 누락 기록을 남기고, 그 기록은 다음 실행에서 reset 표식(메인 차단 사유)이 된다.
  - `HOOK_TIMEOUT_S`는 settings.json의 discipline hook timeout과 같아야 한다(`tests/test_session_store.py` S-T12가 강제).
  - F4a의 `actor(data)`가 `<agent_type>:<agent_id>` 표시를 만든다(허용 문자 제한, 80자).
- `settings.json` 작업 트리에는 사용자의 미커밋 변경(model, enabledPlugins, 키 순서 변경)이 있다. HEAD와 355줄이 다르다.
- `tests/final_check.py`(게이트 밖, 설치 점검 스크립트)의 `want` 표에 hook 등록 목록이 있다.

## 설계 판단
| 방식 | 내용 | 판단 |
|---|---|---|
| A. 수명 기록 + 시작 안내 | 시작·종료를 상태에 기록하고, 시작할 때 subagent에게 추적 규칙을 안내한다. 판정은 그대로 둔다 | **채택** |
| B. SubagentStop에서 차단 | subagent가 미검증 편집을 남기면 끝나지 못하게 한다 | 기각 |
| C. 수명 기준 면제 | subagent가 수명 안에 만들고 지운 저장소는 메인을 막지 않게 한다 | 기각 |

- B 기각: 읽기 전용 subagent나 내부 agent까지 hook 판정에 걸리고, subagent가 스스로 게이트를 돌리며 반복할 위험이 있다. 검증 책임은 메인 턴의 Stop에 이미 있다.
- C 기각: F4a 때와 같은 이유다. P0-04b D3 계약(사라진 저장소는 증명 없이는 미확인, 사용자 확인으로만 해제)과 충돌하고, 주체 표시는 위조 가능한 입력이라 판정에 쓸 수 없다.
- 따라서 F4b도 **차단·허용 판정을 바꾸지 않는다.**

## 설계
### `hooks/discipline.py`
1. 새 모드 `agent-start`, `agent-stop`. `HOOK_TIMEOUT_S`에 각각 30초.
2. 상태 키 `agents: {<주체 표시>: {"started": t, "stopped": t 또는 null, "runs": n}}`를 `default_state`에 추가한다(형식 검사 자동 적용). 키는 `actor(data)`의 결과다.
   - `agent-start`: 항목을 만들거나 갱신한다(`runs` 증가, `stopped`를 null로). 재개도 같은 경로다.
   - `agent-stop`: **시작이 기록된 주체만** `stopped`를 채운다. 기록에 없는 주체(내부 agent 등)는 상태를 바꾸지 않는다.
   - `agent_id`가 없거나 문자열이 아니면 두 모드 모두 아무것도 하지 않는다.
   - 최대 50개. 넘치면 끝난 항목 중 가장 오래된 것부터, 없으면 가장 오래된 것부터 지운다.
3. `agent-start`의 출력: `hookSpecificOutput.additionalContext`(hookEventName `SubagentStart`)로 짧은 안내를 넣는다. 내용은 세 가지다.
   - 이 subagent의 도구 호출은 메인 세션의 추적 상태에 함께 기록된다.
   - 재현용 저장소와 임시 파일은 `%TEMP%` 아래에 만든다.
   - 추적 중인 저장소를 지우거나 옮기지 않는다.
4. `agent-stop`은 어떤 경우에도 출력하지 않는다(subagent를 붙잡지 않는다).
5. 수명 이벤트의 실패 처리: 잠금 실패나 예외가 나도 **누락 기록을 남기지 않고** 로그만 남긴 뒤 exit 0. 수명 이벤트에는 검증에 필요한 정보가 없으므로, 놓쳤다고 세션을 미확인으로 만들 이유가 없다. `pre`, `post`, `fail`, `prompt`, `stop`의 실패 처리는 그대로다.
6. 표시: `owner_note`가 만드는 사유 접미에서, `agents`에 종료가 기록된 주체에는 `(종료됨)`을 붙인다. 표시일 뿐이다.
7. `recover-state`는 `agents`를 넘기지 않는다.

**불변 조건**: `agents`는 어떤 차단·허용 판정에서도 읽지 않는다.

### `settings.json`
`hooks`에 두 항목을 추가한다. matcher는 두지 않는다(내부 agent는 설계 2의 "시작이 기록된 주체만" 규칙으로 걸러진다).

```json
"SubagentStart": [{"hooks": [{"type": "command", "command": "<python> -I C:/Users/user/.claude/hooks/discipline.py agent-start", "timeout": 30}]}],
"SubagentStop":  [{"hooks": [{"type": "command", "command": "<python> -I C:/Users/user/.claude/hooks/discipline.py agent-stop",  "timeout": 30}]}]
```

`<python>`은 기존 hook과 같은 절대 경로다. 다른 키는 건드리지 않는다.

커밋 방법: 작업 트리의 settings.json에는 사용자의 미커밋 변경이 섞여 있다. **이 두 항목만** 커밋한다(HEAD 내용에 두 항목을 더한 blob을 index에 올림). 사용자의 나머지 변경은 미커밋 상태로 그대로 둔다.

### `tests/final_check.py`
`want` 표에 `SubagentStart`, `SubagentStop` 두 줄을 더한다.
