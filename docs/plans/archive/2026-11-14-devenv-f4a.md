# devenv F4a: 세션 상태에 주체(agent_id) 기록

- 마스터 계획: `docs/plans/2026-11-11-devenv-evolution-master.md` (재정렬 순서 3번째)
- 선행 작업: P0-04b 마감 (main 37a1c36, LOCALLY_VERIFIED / CI_PENDING)
- 저장 위치: `docs/plans/2026-11-14-devenv-f4a.md`

## Context
세션 추적 상태는 `session_id` 하나로만 구분된다. 메인 Claude와 subagent의 hook이 같은 상태 파일에 쓰고, 누가 쓴 기록인지는 남지 않는다(F4, P0-S 계획 Context 3).

실제로 겪은 문제: 이전 세션에서 리뷰 subagent가 재현용 저장소(`p3parent` 등)를 만들고 지웠다. 그 저장소가 메인 세션의 추적 대상에 섞여 "저장소가 사라졌습니다" 경고가 턴마다 나왔고, 메인은 그것이 누구의 저장소였는지 알 수 없었다.

마스터플랜의 F4a 정의는 "상태 소유권을 agent_id로 분리", 수용 기준은 "메인·subagent 상태 비혼합 테스트"뿐이고 설계는 없다. 이 계획이 그 설계를 정한다.

## 확인한 사실
- 공식 문서(code.claude.com/docs/en/hooks): subagent가 도구를 부르면 PreToolUse, PostToolUse가 메인과 같은 hook으로 실행되고 입력에 `agent_id`, `agent_type`이 실린다. `agent_type`은 `--agent`로 시작한 메인 세션에도 있을 수 있다. 메인에서 `agent_id`가 없는지 빈 값인지는 문서에 없다(미확인).
- subagent hook의 `session_id`가 부모와 같다는 문장은 문서에 없다. 다만 이 저장소의 hook은 그렇게 동작해 왔다(리뷰 subagent의 셸 기록이 메인 세션 상태에 들어옴).
- subagent 이벤트의 `prompt_id`가 메인 턴의 값과 같은지는 미확인이다. 이 계획은 그 값에 의존하지 않는다.
- `hooks/discipline.py`는 `agent_id`를 읽지 않는다(150행 주석에만 언급). 기존 테스트는 subagent의 게이트 실행을 세션의 증거로 인정한다(`tests/test_discipline.py` 404-415행, 483-491행).
- 저장소를 "건드림"으로 기록하는 곳은 세 군데다: `note_shell_touch`(466행), `on_pre`의 편집 분기(523-526행), `on_post`의 편집 분기(597-599행).
- 누락 이벤트 기록은 `note_safely(path, f"{mode}: ...")`(2395, 2404행)로 남고 다음 실행에서 reset 표식의 사유가 된다.

## 설계 판단
검토한 방식은 세 가지다.

| 방식 | 내용 | 판단 |
|---|---|---|
| A. 주체 기록만 | 상태 항목에 누가 남겼는지 표시한다. 차단 판정은 그대로 둔다 | **채택** |
| B. 주체별 상태 분할 | agent마다 별도 하위 상태(턴 파일 수, 건드린 저장소 등)를 둔다 | 기각 |
| C. subagent 기록 완화 | subagent가 만든 저장소·표식은 메인을 막지 않게 한다 | 기각 |

- C를 기각한 이유: P0-04b의 D3 계약(사라진 저장소는 증명 없이는 미확인, 사용자 확인으로만 해제)과 충돌한다. subagent도 실제 코드를 고칠 수 있으므로 "subagent 것이니 무시"는 미검증 변경을 숨기는 경로가 된다.
- B를 기각한 이유: 턴당 5개 파일 한도, 승인 범위, 검증 증거는 세션 전체에 적용돼야 한다. 나누면 subagent로 한도를 우회할 수 있다. 변경 폭도 크다.
- 따라서 F4a는 **판정을 바꾸지 않는다.** 메인이 여전히 막히지만, 사유에 주체가 적혀 사용자가 `ack-missing` 여부를 판단할 수 있게 된다. subagent 수명에 맞춘 처리(시작·종료 시점 기준선 등)는 F4b(SubagentStart/Stop 등록, settings 변경, 별도 승인)의 몫이다.

## 설계 (최소 변경, `hooks/discipline.py`)
1. `actor(data) -> str`: 이벤트의 주체 표시를 만든다.
   - `agent_id`가 없거나 빈 문자열이면 `"main"`.
   - 문자열이면 `"<agent_type>:<agent_id>"`. 제어 문자는 지우고 80자로 자른다. `agent_type`이 없으면 `"agent"`.
   - `agent_id`가 문자열이 아닌 값이면 `"agent:?"`(메인으로 치지 않는다).
2. 상태 키 `owners: {<저장소 top>: [주체, ...]}`를 `default_state`에 추가한다(형식 검사가 자동 적용됨).
   - `note_owner(state, top, who)`를 위 세 군데에서 부른다. 셸은 직접 대상(`shell_targets`의 저장소)에만 기록한다. "셸은 어디든 쓸 수 있다"는 이유로 전체 저장소를 건드림 처리하는 부분에는 기록하지 않는다(모든 저장소에 subagent 이름이 붙는 것을 막기 위해).
   - 저장소당 최근 8개, 전체 `MAX_DIR_CACHE`(200)개로 제한한다.
   - 저장소가 정상 삭제로 잊히거나 `ack-missing`으로 해제되면 그 항목도 지운다.
3. 편집 기록(`dirty` 항목)에 `by: [주체]`를 더한다. `mark_dirty`에 선택 인자를 추가하고 `reresolve_dirty`가 그대로 넘긴다.
4. 검증 증거(`evidence` 기록)에 `by: 주체`를 더한다.
5. 누락 이벤트 기록의 문구에 주체를 넣는다(`pre[code-reviewer:a1]: ...`).
6. 사유 문구에 주체를 덧붙인다.
   - `REASON_REMOVED`: "이 저장소를 건드린 주체: ..." (subagent가 포함될 때만)
   - `REASON_UNVERIFIED`: 편집 주체에 subagent가 있으면 그 이름
7. `ack-missing` 감사 줄에 `owners`를 추가한다.
8. `recover-state`는 `owners`를 넘기지 않는다(표시일 뿐이고, 표식 루트는 기존대로 모든 장소를 덮는다).

**불변 조건**: `owners`와 `by`는 어떤 차단·허용 판정에서도 읽지 않는다. 사유 문구와 감사 기록에만 쓴다.

## 위험
- F4a만으로는 subagent가 만든 표식이 메인을 막는 일이 없어지지 않는다. 주체가 보일 뿐이다. 근본 처리는 F4b 이후에 다시 판단한다.
- `agent_id`는 harness가 주는 값이지만 hook 입장에서는 외부 입력이다. 표시에만 쓰고 판정에 쓰지 않으므로, 값이 위조돼도 차단이 풀리지 않는다. 사유 문구에 들어가므로 길이와 제어 문자를 제한한다.
- 메인 이벤트의 `agent_id` 형태가 문서에 없다. 빈 문자열과 없음을 모두 메인으로 본다. 실제 값이 다르면 메인이 `agent:?` 등으로 표시될 수 있다(표시 오류일 뿐 판정에는 영향 없음). 3단계 뒤 이 세션의 상태 파일로 실제 값을 확인한다.
- 상태 파일에 키가 늘어난다. 이전 버전 hook이 쓴 상태에는 `owners`가 없으므로 없는 경우를 기본값으로 다룬다.
