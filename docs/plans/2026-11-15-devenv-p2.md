## Context
마스터 계획의 순서는 P0 → P1 → P3 → P2이고, P2의 채택 기준은 "P3 실험에서 비열등이고 효과 구간을 보고, 효과가 없으면 채택하지 않음"이다. P3의 도구는 완성됐지만 실제 평가(P3-01과 공식 실행)는 사용자의 작업을 기다린다. 그래서 P2는 **효과를 판정할 수 없는 상태에서 시작한다.** 이 계획의 결정: P2 항목을 만들되 어느 것도 "채택"하지 않는다.

- 새 판정은 관측만 한다(기록하고, 필요하면 한 번 알린다). 아무것도 막지 않고, 기본 모델·기본 설정·승인 절차를 바꾸지 않는다.
- 항목마다 끌 수 있는 환경 변수를 두고, 끄면 그 항목이 없던 때와 같게 동작한다(P3에서 조건 A/B로 쓰기 위해서다).
- 항목이 끝나면 `eval-harness`의 제안 큐 형식에 맞춘 제안 한 줄(id, 제목, 상태 `proposed`)을 그 항목의 계획 문서에 적는다. 큐 파일 자체는 평가자 환경이 생긴 뒤에 만든다.
- 마스터 계획의 체크는 "구현되어 관측 중"이라는 뜻으로 하고, 현황 줄에 "효과 미판정"을 적는다.

사용자가 P3 평가를 먼저 끝내고 싶어 하면 이 단계는 어느 항목 뒤에서든 멈출 수 있다(항목들은 서로 독립이다).

## 공통 규칙 (P1과 같다)
- 순서대로 하나씩: 계획 → 테스트 먼저(실패 확인) → 구현 → 게이트(`python -I tests/run_all.py`) → code-reviewer 1회 → 반영 → 게이트 → 커밋 → push → CI 확인 → 마감 기록.
- hook에 넣는 작업은 지연을 잰다. P1 마감 값(`tests/_baseline/2026-11-11-post-p1.json`)보다 hook당 p50이 30ms 넘게 늘면 원인을 적고 줄인다(초기 값).
- 기록은 숫자와 분류만 담는다(경로·내용·명령 원문 없음). 기록은 승인을 주거나 되살리는 데 쓰이지 않는다.
- 하지 않는 일: Quant 저장소와 그 데이터 경로의 읽기·변경, 운영 설정의 강제 전환, 새 subagent·skill·MCP 서버·메모리 DB 추가, 메모리나 Gotchas의 자동 반영, 기본 모델 변경.

## 항목

### P2-01 위험 점수와 P2-03 대안 비교 안내 (마스터 32번)
- 문제: 변경의 위험은 지금 "파일 5개 초과" 하나로만 본다. hook·설정·CI·의존성·스키마를 건드리는 한 줄 변경과 문서 열 줄 변경이 같게 취급된다.
- 할 일: 한 턴의 변경에서 위험 점수를 계산하는 순수 함수(입력: 바뀐 파일 수, 경로의 종류(코드·테스트·문서·설정·CI·의존성 잠금·hook), 바뀐 줄 수, 저장소 수). Stop에서 점수와 그 구성 요소를 관측 기록에 남긴다. 점수가 기준을 넘는데 승인된 계획에 대안 비교가 없으면(계획 본문에 선택지 표나 "대안"·"옵션" 절이 없음) "대안 2~3개를 비교하라"는 안내를 한 번 넣는다(막지 않음).
- 재사용: `discipline.py`의 `path_class`, `is_test_file`, `_repo_place`, 관측 기록 방식(`note_test_gap`).
- 완료 기준: 점수 함수의 경계값 테스트, 문서만 바뀐 턴은 0에 가깝고 hook·CI·잠금 파일은 높다, 안내는 턴당 한 번, 끄는 변수로 완전히 꺼진다.

### P2-02 모델 라우팅 실험 (마스터 33번)
- 할 일: 기본값은 최고 성능 모델로 둔다. 라우팅은 "실험 설계"만 만든다: `eval-harness`의 사전 등록 문서 틀(조건 A = 기본 모델, 조건 B = 환경 변수로 지정한 다른 모델, 주 지표 완료율, 비열등 한계)과 실행 방법을 문서로 쓴다. 실행은 평가자 환경이 생긴 뒤다.
- 저장소: 틀과 문서는 `C:\dev\tools\eval-harness`(dev-tools)에 둔다. 조건이 모델을 바꾸는 환경 변수 이름은 공식 문서로 확인한다(미확인).
- 완료 기준: 틀이 `eval-harness prereg lock`으로 잠기고 검증을 통과한다(테스트). 운영 설정에는 변화가 없다.

### P2-04 실패 재발 감지와 Gotchas 후보 제안 (마스터 34번)
- 문제: 같은 종류의 실패(게이트 실패, CI 실패 분류)가 세션을 넘어 반복돼도 알 수 없다. Gotchas는 그때그때 손으로 적는다.
- 할 일: 실패의 종류(P1-05의 CI 분류, 게이트 실패한 검사 이름)를 저장소별로 세는 기록을 둔다. 같은 종류가 정해진 기간 안에 기준 횟수(초기 2회) 이상이면 세션 시작 안내에 "Gotchas 후보"로 한 줄을 보여 준다. CLAUDE.md에는 쓰지 않는다.
- 재사용: `ci_status.classify_failure`, `session_context.ledger_section`의 안내 방식, `redact.redact`.
- 완료 기준: 재발 1회에서는 침묵, 기준 도달 때 한 줄, 다른 저장소와 섞이지 않음, CLAUDE.md 변경 없음.

### P2-05 메모리 검색 (마스터 35번)
- 문제: 자동 메모리는 작업 폴더별로 나뉘어 있어, 다른 폴더에서 시작한 세션은 관련 메모리를 보지 못한다(CLAUDE.md §2b).
- 할 일: 메모리 파일(frontmatter의 name·description과 본문)을 낱말로 찾는 읽기 전용 명령 하나(`hooks/memory_search.py`). 찾을 폴더는 인자로 받고 기본은 현재 프로젝트의 메모리 폴더다. 결과는 파일 이름, 한 줄 설명, 일치한 줄. 색인·DB를 만들지 않는다. 메모리를 옮기거나 고치지 않는다(P0-11은 별도 승인 항목으로 남는다).
- 완료 기준: 임시 폴더의 예시 메모리로 한 테스트(일치, 불일치, 깨진 frontmatter, 큰 파일 한도), 출력에 비밀 형태 문자열이 가려진다.

### P2-06 `/implement`와 원장 연동 (마스터 36번)
- 할 일: `/implement`가 계획을 다시 시작할 때 원장의 그 작업 마지막 상태(검증 상태, 리뷰 판정, 시각)를 읽어 "어디까지 검증됐는지"를 알고 시작하게 한다. 원장을 읽는 작은 명령(`python -I hooks/ledger.py show --task <id>`)과 skill 문서의 절차 한 단락. 승인 절차는 그대로다(원장은 승인을 주지 않는다).
- 완료 기준: 명령의 출력 테스트(기록 있음, 없음, 변조된 원장은 경고), skill 문서의 변경은 절차 설명에 한정.
