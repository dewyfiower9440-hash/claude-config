## Context
승인된 계획의 범위 판정(`in_approved_scope`, `hooks/discipline.py:1082`)에 구멍이 세 개 있다.

1. **다른 저장소의 계획 폴더도 범위 안으로 본다(N1).** 경로에 `/docs/plans/`만 들어 있으면 어느 저장소든 허용한다(1093행). 승인은 한 저장소의 한 계획에 대한 것인데, 다른 프로젝트의 계획 파일까지 고칠 수 있다.
2. **코드 승인이 데이터 경로까지 덮는다(C2).** 범위에 넓은 패턴(예: `C:/dev/**`)이 있으면 git 밖의 폴더(원본 데이터, 백업)도 같은 승인으로 허용된다. git 밖은 변경 감지도 되지 않는다.
3. **범위 목록에 설명 줄이 섞인다.** `## 변경 범위` 아래의 `- 범위 밖: ...` 같은 설명 줄에서 첫 단어를 경로 패턴으로 읽는다(`plan_scope`, 814행).

목표: 승인이 실제로 덮는 경로를 "승인받은 저장소의 계획 폴더", "범위 패턴에 맞는 저장소 안 파일", "따로 선언한 데이터 경로"로 좁힌다.

## 확인한 사실
- `in_approved_scope(approval, path)`는 두 곳에서 쓴다: 쓰기 전 판정(`on_pre`, 698·701행)과 Stop의 범위 검사(`_scope_decision`, 2392행). 이 함수만 바꾸면 두 곳에 함께 적용된다.
- v2 포인터에는 승인받은 git root가 `base`로 들어 있다(1309-1316행, `v2_rearm` 1390행).
- `plan_scope(text, base)`는 v1 발급(914행)과 v2 발급(1288행)에서 호출한다. 결과 목록은 v2 기록의 `scope`로 서명·저장된다.
- 저장소 여부를 git 없이 판정하는 기존 함수가 있다: `may_be_repository(path)`(99행). 상위 폴더에 `.git`이 하나도 없을 때만 False다.
- 링크를 따라간 실제 경로까지 함께 보는 기존 방식이 있다: `ignored_path`(124행).
- `tests/test_approvals.py`는 현재 299초다(상한 350초 prior). 새 테스트를 여기에 더하면 넘는다.
- `tests/bench_hooks.py`의 공격 코퍼스에 N1 사례가 있다(314행). 게이트 대상은 아니다.

## 설계
### 1. 경로 클래스 (순수 함수)
`path_class(real_path, base, in_repo) -> "plan" | "code" | "data" | "external"`
- `plan`: `<base>/docs/plans/` 안
- `code`: `base` 안의 그 밖의 파일
- `data`: `base` 밖이고, 어떤 git 저장소에도 들어 있지 않음이 확실함(`in_repo`가 False)
- `external`: `base` 밖이고, 다른 저장소 안이거나 판단할 수 없음

판정은 링크를 따라간 실제 경로(`os.path.realpath`)로 한다. `in_repo`는 호출부에서 `may_be_repository`로 구해 넘긴다(I/O는 바깥).

### 2. 범위 판정 변경 (`in_approved_scope`)
| 클래스 | 허용 조건 |
|---|---|
| plan | 항상 허용. 단 주어진 경로와 실제 경로가 **모두** `<base>/docs/plans/` 안일 때만. 다른 저장소의 계획 폴더는 예외가 아니다 |
| code | 지금과 같다: `## 변경 범위` 패턴에 맞을 때 |
| external | 지금과 같다: `## 변경 범위` 패턴에 맞을 때 (다른 저장소 전환은 P0-10에서 다룬다) |
| data | `## 데이터 변경 범위` 패턴에 맞을 때만. `## 변경 범위` 패턴으로는 허용하지 않는다 |

- `base`가 없는 승인 기록(옛 v1 형식)은 계획 폴더 예외를 받지 못한다(닫힌 쪽).
- 범위가 비어 있는 승인의 기존 규칙(자기 프롬프트에만 적용)은 그대로다.

### 3. 계획 파싱 변경 (`plan_scope`)
- `## 데이터 변경 범위` 블록의 항목을 읽어 `data:<절대 패턴>` 형태로 같은 목록에 넣는다. 저장 형식(서명되는 `scope` 목록)은 그대로라 `approvals.py`와 저장소 구조는 바꾸지 않는다.
- 설명 줄은 건너뛴다: 목록 항목에서 드라이브 문자가 아닌 `:` 앞에 단어가 둘 이상 있고 백틱이 없으면 경로가 아닌 설명으로 본다(예: `- 범위 밖: 다른 파일`).
- 블록이 계획 본문에 있으므로, 블록을 더하거나 고치면 계획 해시가 바뀌어 다시 승인받아야 한다(기존 동작).

### 검토한 대안
| 방식 | 판단 |
|---|---|
| A. 클래스 + 같은 목록에 `data:` 접두사 | **채택**: 저장소 구조 변경 없음 |
| B. v2 기록에 `data_scope` 필드 추가 | 기각: 서명 대상과 저장 형식이 바뀌어 운영 저장소 이관이 필요하다 |
| C. 데이터 폴더를 이름으로 지정(설정 목록) | 기각: 목록에 없는 git 밖 폴더가 계속 뚫린다 |

- git 밖 경로를 범위에 넣어 쓰던 계획은 `## 데이터 변경 범위`로 옮기기 전까지 그 경로가 거부된다(의도한 변경). 현재 진행 중인 계획에는 그런 경로가 없다.
