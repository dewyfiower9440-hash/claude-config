- 이 문서는 범위 정의와 막힌 이유의 기록이다. 코드나 환경을 바꾸지 않았다.

## 왜 여기서 멈추는가
1. **평가의 전제가 격리다.** 숨은 테스트와 채점 기준은 개발 계정(이 계정)이 읽을 수 없는 곳에 있어야 한다(마스터 계획: "평가 과제를 개발 계정에서 읽을 수 있게 두지 않습니다"). 이 계정에서 테스트를 쓰면 대화 기록(`~/.claude/projects`)에 남아 격리가 깨진다. 그래서 숨은 테스트의 작성과 채점은 평가자 쪽 환경에서 돌아가는 별도의 Claude Code가 해야 하고, 그 환경의 비밀번호와 로그인은 사용자만 가져야 한다. 이 계정의 에이전트가 대신 만들 수 없다.
2. **사용자가 따로 승인하겠다고 정한 항목이다.** 마스터 계획 25번("evaluator 계정과 구독 사용량은 별도 승인"), 초안의 승인 경계("VM 생성·암호화, 권한·ACL 변경, 외부 로그인, GitHub 저장소 생성, 비공개 테스트 작성, Dry Run, 공식 14회 실행"), 사용자 지시("Windows ACL, 사용자 계정 ... 변경은 별도 승인 항목"). 2026-11-14의 상시 승인("앞으론 승인안받아도된다")이 이 항목들까지 푸는지는 내 해석으로 정하지 않는다. 풀린다 해도 1번 때문에 사용자의 직접 작업이 필요하다.
3. **실행 순서가 고정이다**(P0 → P1 → P3 → P2). P2의 채택 기준은 P3의 평가 결과다(마스터 계획: "P3-01~03 이후에만 효과를 판정"). P3를 건너뛰고 P2를 구현하면 효과를 판정할 수 없는 변경이 쌓인다.

## 항목별 범위 (승인 뒤에 각자 계획을 쓴다)
- **P3-01 평가자 환경, 과제 저장소, 홀드아웃**: 위 1·3·5번. 완료 기준: 개발 계정에서 숨은 테스트를 읽으려 하면 거부되고(실제 시도로 확인), 과제 저장소의 기준 커밋이 고정돼 있다.
- **P3-02 headless 실행기와 숨은 테스트 채점**: 과제 프롬프트를 조건별로 `claude -p`로 실행하고(실행기, 개발 계정), 결과 브랜치를 평가자 환경에서 숨은 테스트로 채점한다(채점기). 에이전트의 "완료" 주장은 채점에 쓰지 않는다. 가짜 실행 파일로 실행기를 시험할 수 있어, 환경이 없어도 실행기 코드는 만들 수 있다.
- **P3-03 지표**: 완료율(숨은 테스트 통과), 거짓 완료율(완료라고 했지만 통과하지 못함), 범위 밖 변경, 테스트 약화, CI 결과와의 일치. 입력은 채점 결과와 P1에서 만든 기록(작업 원장 `~/.claude/state/ledger/`, 관측 기록 네 가지). 순수 계산이라 환경 없이 만들 수 있다.
- **P3-04 사전 등록**: 실행 전에 가설, 지표, 표본 수, 분석 방법(Wilson 95% 구간)을 문서로 고정하고 해시를 남긴다. 실행 뒤에 바꾸면 드러나게 한다.
- **P3-05 개선 루프**: 제안 큐 → 평가 → 채택·롤백의 절차와 기록 형식. 채택 기준은 사전 등록에 적는다.

## 환경 없이 먼저 만들 수 있는 것 (승인되면 바로 시작)
- P3-03의 지표 계산과 Wilson 구간(순수 함수, 테스트 포함), P3-04의 사전 등록 형식과 해시 검증, P3-02의 실행기(가짜 `claude` 실행 파일로 시험).
- 위치 결정(위 4번)이 필요해서 시작하지 않았다. `~/.claude` 저장소는 설정·hook만 추적하게 돼 있고(`.gitignore`의 허용 목록), 공용 도구는 `C:\\dev\\tools`에 두는 것이 이 환경의 규칙이다(CLAUDE.md §0).

## P1이 P3에 넘겨주는 것
- 작업 원장: 작업별 검증 상태의 변화와 리뷰 판정(P1-01, P1-02).
- 관측 기록: 승인 없는 편집(P0-06), 리뷰가 없는 검증된 변경(P1-02), 테스트 없는 턴(P1-03), 큰 출력(P1-04). 모두 경로·내용 없는 숫자다.

- 이 기록들은 같은 계정의 파일이라 평가의 근거로는 약하다. 채점의 근거는 숨은 테스트와 CI 결과이고, 이 기록은 보조 지표다.
