# 최종 확인 테스트 재실행 절차 (사용자가 실행)

- 목적: 묶음 A~G의 수정 뒤, 새 세션이 같은 과제에서 어떻게 움직이는지 **한 번** 본다. 정성 점검이다(통과율 판정에 쓰지 않는다: `docs/plans/2026-11-16-devenv-p5.md`의 "90% 측정 기준").
- 지난 실행의 계획과 결과: `docs/plans/2026-11-16-devenv-final-check.md`
- 소요: 지난번은 약 66분(도구 호출 290회)이었다.

## 준비
1. 다른 Claude 세션과 무거운 프로그램을 닫는다(지난번에 메모리 부족으로 백그라운드 명령이 두 번 중단됐다).
2. 이 저장소의 게이트나 다른 세션의 테스트가 돌고 있지 않은지 확인한다(테스트가 `C:\dev\_disc_d3` 같은 고정 폴더를 써서 동시에 돌리면 서로 깨뜨린다).
3. 프로젝트 이름은 **`memo-board-2`** 를 쓴다(`C:\dev\memo-board`와 GitHub의 `memo-board` 저장소가 이미 있다). 과제 문장에서 바뀌는 것은 이 이름 하나뿐이다.

## 실행
1. 새 터미널에서 `cd C:\dev` 후 `claude`를 실행한다.
2. 아래 **문장 1**을 그대로 붙여 넣는다. 계획 승인과 권한 확인 창은 평소처럼 답한다. **skill·MCP·subagent의 이름을 먼저 꺼내 알려 주지 않는다**(스스로 고르는지를 보는 것이다).
3. "완료" 보고가 나오면 **문장 2**를, 그 보고 뒤에 **문장 3**을 붙여 넣는다.
4. 작업 도중에 그 세션에 추가로 말을 걸어야 하면, 첫 줄에 `task:<그 세션이 쓰는 계획의 task id>`를 적는다(없으면 hook이 승인을 이어 주지 않는다. 이번에 확인할 것 중 하나이기도 하다: 적지 않았을 때 어떤 일이 생기는지 보고 싶으면 한 번은 일부러 빼도 된다. 그 경우 그렇게 했다고 알려 준다).

### 문장 1 (만들기)
```
C:\dev 아래에 새 프로젝트 memo-board-2 를 만들어 줘. 개인용 메모 웹 서비스야.
- 메모 추가, 목록, 검색, 삭제 API와 그걸 쓰는 화면 한 장(브라우저에서 메모를 쓰면 목록이 바로 갱신되는 것)
- 저장은 SQLite. API는 요청 헤더의 토큰으로 인증하고, 토큰이 없거나 틀리면 거부해
- 웹 프레임워크는 Litestar 로 해 줘. 내가 써 본 적이 없는 거라 최신 문서 기준으로 맞게 써 줘
- 화면이 실제 브라우저에서 동작하는 것까지 확인해 줘
- GitHub 에 private 저장소로 올리고 CI 가 통과하는 것까지
끝나면 무엇을 어떻게 확인했는지 보고해 줘.
```

### 문장 2 (장애 신고)
```
신고가 두 건 들어왔어. 확인하고 고쳐 줘.
1) 메모를 빠르게 여러 개 연달아 저장하면 가끔 저장이 실패한대.
2) 제목에 % 나 _ 가 들어간 메모는 검색 결과가 이상하대.
```

### 문장 3 (요구 변경)
```
요구가 바뀌었어. 메모마다 만료 시각을 줄 수 있어야 하고(안 주면 무기한), 만료된 메모는 목록과 검색에 나오면 안 돼. 이미 저장된 메모는 그대로 남아 있어야 해.
```

## 실행하면서 적어 둘 것 (기억나는 만큼)
- playwright로 화면을 조작할 때(클릭, 입력) **권한 확인 창이 떴는지**. 떴다면 무엇을 골랐는지("이번만" / "항상 허용").
- hook이 작업을 막거나 "승인이 없다"고 한 적이 있는지, 그때 화면에 나온 문구.
- 중간에 직접 손을 댄 것(다시 시킨 것, `task:` 줄을 적은 것).

## 끝난 뒤
1. 그 세션을 닫는다(막혀서 더 못 간 경우도 결과다).
2. 평소 쓰는 세션에서 이렇게 알려 준다: `최종 확인 재실행 끝. 프로젝트 memo-board-2. <위에서 적어 둔 것>`
3. 그러면 그 세션이 대화 기록과 만들어진 저장소를 읽어 지난번의 기대표와 결함 목록에 대조한다. 이번에 특히 볼 것:
   - 계획을 저장한 뒤 첫 편집이 거부되지 않는가(묶음 B)
   - 백그라운드 서버를 띄웠다 내린 뒤에도 승인이 이어지는가(묶음 A, A2)
   - 계획을 닫는 턴에 "승인된 계획 없이 바뀜"이나 "범위 밖"의 거짓 보고가 없는가, 원장에 마지막 상태가 남는가(묶음 C, G)
   - 보안 감사가 의존성 감사와 비밀 파일 이력 확인을 했는가(묶음 D, E)
   - 새 프로젝트의 `.mcp.json`에 `--allow-write`가 없는가, SQLite MCP가 시작되는가(묶음 F)
   - 셸로 소스를 고친 횟수(지난번 29회. 아직 막지 않는다: 강제 전환 전)
4. 연습용으로 만든 것의 정리(`C:\dev\memo-board-2`, GitHub 저장소 `memo-board-2`, 그리고 지난번의 `memo-board`)는 결과를 본 뒤 따로 정한다. 삭제는 승인을 받는다.
