# devenv: 품질 게이트 실행 시간 근본 해결 (모듈 병렬 실행)

## Context
- 게이트 `python -I tests/run_all.py` 실측 시간은 **699초**(2026-11-12)입니다. 포그라운드 도구 상한(600초)을 넘어서 hook이 게이트 증거를 한 번도 인정하지 못하고 있습니다.
- 원인은 실측으로 확인했습니다(cProfile).
  - 시간 대부분은 hook을 별도 프로세스로 실행하고 기다리는 데 씁니다.
    - test_approvals: hook 호출 311회, 144초(회당 0.46초)
    - test_discipline: hook 호출 388회, 138초(회당 0.36초)
  - 회당 비용은 Python 기동과 git 호출(toplevel 약 70ms, 내용 맵 약 230ms)입니다.
  - `run_all.py`는 이런 모듈 12개를 **한 개씩 순서대로** 실행합니다(`run_all.py:63-64`). 그래서 전체 시간은 각 모듈 시간의 합이 됩니다.
- 모듈끼리는 서로 독립적입니다.
  - 각 모듈은 자기 전용 임시 디렉터리를 씁니다(`_tmp_approval_*`, `_tmp_store`, `_tmp_disc*`/`C:/dev/_disc_*`, `_tmp_wt*`, `_tmp_ci`, `_tmp_verification`, `mkdtemp(prefix=...)`).
  - 세션 상태 파일은 uuid로 이름을 붙여 겹치지 않습니다.
  - 승인 저장소 경로는 프로세스마다 환경변수로 따로 지정합니다.

## 접근 방식 (권장안)
**같은 명령, 같은 테스트, 같은 판정 기준을 그대로 두고 모듈 실행만 병렬로 바꿉니다.**
- ruff check와 ruff format은 지금처럼 먼저 순차로 실행합니다.
- 테스트 모듈 12개는 `concurrent.futures.ThreadPoolExecutor`로 동시에 실행합니다. 각 모듈은 지금처럼 별도 `subprocess.run`으로 실행하고, 동시 실행 수는 기본 3입니다.
  - 3은 임시값입니다. RAM 16GB와 상주 수집기를 고려해 정했고, 측정 후 다시 조정합니다.
  - 환경변수 `GATE_WORKERS`로 바꿀 수 있습니다. `1`이면 지금처럼 순차로 돕니다.
- 오래 걸리는 모듈(test_approvals, test_discipline, test_guard_corpus)부터 먼저 제출합니다. 전체 시간을 가장 긴 모듈 하나에 가깝게 맞추기 위해서입니다.
- 출력과 판정은 지금과 같습니다.
  - 결과 출력은 **선언된 TESTS 순서 그대로** 합니다. 각 모듈의 PASS/FAIL 줄, 실패 시 마지막 3000자, ALWAYS_SHOW 규칙은 바뀌지 않습니다.
  - 하나라도 실패하면 GATE FAILED, exit 1입니다.
  - 각 모듈 줄에 소요 시간(초)을 덧붙입니다. 측정 근거를 남기기 위해서입니다.
- 예상 시간은 약 150~260초입니다(가장 긴 모듈 149초 + 나머지 분배). 이 숫자는 실측으로 확인합니다.

다른 대안을 택하지 않은 이유:
- 테스트를 줄이거나 지우는 방안은 금지 사항입니다.
- 테스트 안에서 hook을 프로세스 없이 호출하는 방안은 Python 기동 비용만 줄어듭니다. git 비용이 남아 효과가 약 25%(추정)에 그치고, 실제 hook과 동작이 달라질 위험이 있습니다.
- hook 안의 git 호출을 줄이는 방안은 실사용 지연에도 도움이 되지만 증거 판정 로직을 건드립니다. 그래서 이번이 아닌 별도의 측정 기반 과제로 제안합니다.

## 이전 지시와의 관계 (명시)
- 이전에 받은 "테스트·리뷰 순차 실행" 지시는 에이전트나 게이트를 **동시에 여러 개 돌리지 말라**는 뜻으로 이해했습니다.
- 이 계획은 **게이트 하나 안에서** 모듈을 병렬로 실행합니다. 게이트 실행 방식 자체가 바뀌므로, 이 계획을 승인하시면 그것으로 해당 변경을 승인하신 것으로 봅니다.
- 게이트는 이번에도 한 번에 하나만 실행합니다.
