## Context
작업이 어느 검증 상태까지 갔는지(구현만 됨, 로컬 게이트 통과, CI 통과)는 지금 세션 상태 파일에만 있다. 세션이 끝나면 사라지고, 다음 세션은 계획 체크박스와 사람이 쓴 요약에 의존한다. Stop hook이 이미 계산하는 증거에서 상태를 뽑아 저장소별 기록으로 남긴다. 이 기록은 P1-06(재시작 복구)과 P3(완료율·거짓 완료율 측정)의 입력이 된다.

## 확인한 사실
- Stop 때 `refresh_content`가 프로젝트(정책 루트)별로 `state["content"][root] = {digests, pushed, gate, ci}`를 만든다(`hooks/discipline.py:2440-2449`). 통과한 검사는 `state["evidence"][root]`에 내용 해시와 함께 남는다.
- 완료 판정 `_content_decision`(`:2723-2789`)의 규칙: 증거가 passed이고 해시가 현재 내용과 같으면 로컬 검증 완료. `ci: required`이면 모든 저장소가 push됐고, push된 커밋의 CI 결과가 그 push 뒤에 읽혔고 `verified`여야 한다.
- 승인된 작업은 `state["approval"] = {task_id, approval_id, base(git 루트), scope, ...}`로 가리킨다(`:1550-1557`).
- 저장소별 기록 저장 방식의 선례: `hooks/handoff.py`의 `key(root)`(경로 해시 24자)와 `~/.claude/state/handoff/`. 잠금 선례: `session_store.locked`.

## 설계
### 1. 순수 모듈 `hooks/ledger.py`
- 상태 이름(CLAUDE.md §1.6): `IMPLEMENTED`, `LOCALLY_VERIFIED`, `CI_VERIFIED`, 그리고 실패 쪽 `BLOCKED`(게이트 또는 CI 실패), `UNKNOWN`(결과를 읽을 수 없음).
- `root_state(content_entry, evidence, pushes, ci) -> str`: `_content_decision`과 같은 규칙으로 프로젝트 하나의 상태를 낸다. 알림 여부(이미 보고했는지)는 보지 않는다.
- `task_state(states) -> str`: 여러 프로젝트가 걸린 작업은 가장 낮은 상태를 따른다(BLOCKED < UNKNOWN < IMPLEMENTED < LOCALLY_VERIFIED < CI_VERIFIED).
- `make_entry(prev, fields, secret) -> dict`와 `verify(entries, secret) -> 문제 | None`: 각 줄은 허용 목록의 키만 담는다(`v, at, task, approval, state, content, roots, session, prev, mac`). `content`는 내용 해시들을 다시 해시한 짧은 값, `prev`는 앞 줄의 해시, `mac`은 줄 내용의 HMAC-SHA256이다.
- `latest(entries) -> {task: entry}`.

### 2. 저장 (`hooks/ledger.py`의 I/O 부분)
- 위치 `~/.claude/state/ledger/<저장소 경로 해시>.jsonl`(환경 변수 `CLAUDE_LEDGER_HOME`으로 변경 가능, 테스트용). HMAC용 값은 같은 폴더의 `mac-secret`(처음 쓸 때 생성).
- 추가는 잠금(`session_store.locked`, 0.5초) 안에서 마지막 줄을 읽고 한 줄을 덧붙인다. 잠금을 못 얻으면 이번에는 기록하지 않는다(상태가 그대로면 다음 Stop이 기록한다).
- **상태나 내용 해시가 그 작업의 마지막 줄과 다를 때만** 추가한다. 같은 상태의 반복 Stop은 줄을 만들지 않는다.

### 3. hook 연결 (`hooks/discipline.py`의 `on_stop`)
- `refresh_content` 뒤, 판정을 내보내기 전에 `record_ledger(state)`를 부른다. 조건: 승인 포인터가 있고, 그 승인의 git 루트 안에 이번 세션에서 내용이 바뀐 프로젝트가 있을 때.
- 실패(파일, 잠금, 형식)는 로그만 남기고 Stop의 판정과 종료 코드에 영향을 주지 않는다. git 호출을 추가하지 않는다(이미 계산된 값만 쓴다).
- 원장은 어떤 판정의 입력으로도 쓰지 않는다(쓰기 전용). 읽는 쪽은 P1-06에서 만든다.

### 검토한 대안
| 방식 | 판단 |
|---|---|
| A. Stop 때 증거에서 상태를 뽑아 변화만 기록 | **채택**: 판정 규칙이 한 곳(순수 함수)에 있고 hook 비용이 Stop 한 번의 파일 추가뿐 |
| B. 편집·게이트·push 이벤트마다 전이를 기록 | 기각: 이벤트 순서와 누락 처리가 복잡해지고 모든 hook이 느려진다 |
| C. 승인 저장소(v2)에 상태를 함께 저장 | 기각: 승인과 상태를 섞지 않는다(마스터 계획의 원칙) |

## 위험
- 원장의 HMAC 값은 같은 사용자 계정의 파일이다. 에이전트가 읽고 위조할 수 있으므로 이 서명은 실수로 인한 손상과 단순한 수정만 드러낸다. 의도적 위조에 대한 방어는 P3의 평가 계정 분리가 맡는다(문서에 명시).
- 끝부분을 잘라 낸 것(마지막 줄들의 삭제)은 연결 해시만으로는 알 수 없다. 단계 계획의 "잘림 검출"은 가운데 삭제·수정에 한정된다(한계로 기록).
- `root_state`가 `_content_decision`과 어긋나면 원장이 Stop의 판정과 다른 상태를 적는다. 두 규칙이 같은지 R-T14~R-T15(hook 실행)와 리뷰로 확인하고, 어긋남이 생기면 Stop의 판정이 기준이다.
- 편집 추적만 되는 프로젝트(내용 추적이 안 되는 경우)는 `state["content"]`에 없어 기록되지 않는다(한계로 기록).
- live hook의 Stop 경로를 고친다. 원장 쪽 예외가 Stop을 깨지 않게 구체적 예외만 잡고 로그를 남긴다.
