## Context
2026-11-12 감사에서 실제 결함 두 가지와 부수 결함 하나를 확인했다. 근거는 상태 파일, 트랜스크립트, 합성 재현이다.

1. **relay 처리**: subagent 보고와 다른 세션 메시지에도 UserPromptSubmit이 실행된다. 이 동작은 공식 문서에 명시되어 있다. 이때 `on_prompt`가 다음을 초기화한다.
   - 승인
   - `turn_files`, `turn_shell_tops`
   - 턴 기준선
   
   그 결과는 두 가지다.
   - 유효한 승인이 사라져 Stop 판정이 실제 승인 이력과 어긋난다.
   - relay가 올 때마다 무승인 5파일 한도가 다시 0부터 세어져 우회할 수 있다.
2. **TEMP worktree**: `IGNORED_PATH`의 `%TEMP%` 분기(`discipline.py:76`)가 git 작업 트리인지 확인하지 않고 경로 전체를 제외한다. 그래서 Edit/Write의 사전 검사가 모두 생략된다(`:254`, `:267`, `:318`). 생략되는 검사는 승인, 5파일 한도, 약화 검사, 파일 집계다.
3. **삭제된 worktree**: 추적 중인 저장소가 삭제되면 `refresh_content`가 Stop 때마다 그 저장소를 unknown으로 보고한다(`:1430-1432`). 같은 보고가 턴마다 반복된다.

## relay 출처 판별 가능성: 검증 결과와 결론
조사 근거: Claude Code 2.1.322, 공식 문서 https://code.claude.com/docs/en/hooks (UserPromptSubmit, SubagentStop, Common input fields), /sub-agents.

- UserPromptSubmit 입력에는 typed 프롬프트와 주입 메시지를 구분하는 **공식 필드가 없다**(is_meta, origin, source 모두 없음). 주입 메시지를 직전 SubagentStop과 연결하는 상관 id도 문서에 없다.
- 트랜스크립트의 `isMeta`는 문서화되지 않은 형식이다. 게다가 같은 사용자 권한이면 그 파일을 수정할 수 있다. 따라서 신뢰할 출처가 아니다.
- SubagentStop은 settings.json에 등록해야 쓸 수 있는데, 이번 범위 밖이다. background 실행이나 SendMessage 재개 때 실행되는지도 **미확인**이다.
- **결론**:
  - 이번 범위에서는 relay를 신뢰할 수 있는 방식으로 식별할 수 없다.
  - 그래서 relay 이후 승인을 유지하는 기능(R1)은 **구현하지 않는다**. 문자열로 판별해 권한을 넓히는 수정은 금지되어 있다.
  - relay 뒤에는 승인을 잃는 현재의 안전한 차단을 유지한다.
  - 사용자는 다음 프롬프트 첫 줄에 `task:<id>`를 적어 재개한다.
  - 문자열 판별은 **권한을 줄이는 쪽(더 엄격한 쪽)에만** 쓴다. 집계 유지가 여기에 해당한다. 위조 헤더가 들어와도 결과가 더 엄격해질 뿐이다.

## 설계 (최소 변경, `hooks/discipline.py`만 수정)

### D1. relay 형식 프롬프트의 집계 보존 (권한을 줄이는 방향만)
- 판별 기준은 첫 비어 있지 않은 줄이다. 기존 `RELAY_HEADERS`(`another claude session`, `[system notification`)이거나 `<task-notification>`으로 시작하면 relay 형식으로 본다.
- relay 형식 프롬프트를 받으면:
  - **유지하는 것**: `turn_files`, `turn_shell_tops`, 턴 기준선(`refresh_turn_baselines`를 건너뜀). 결과적으로 Stop의 turn_changes와 5파일 한도는 마지막 비 relay 프롬프트부터 누적된다.
  - **유지하지 않는 것**: 승인. 지금처럼 승인을 비우고 재무장도 하지 않는다. v1과 v2 모두 같다.
  - **경고**: `NOTE`로 "relay 메시지로는 승인이 유지되지 않음 — 사용자 프롬프트 첫 줄에 task:<id>로 재개"를 알린다.
- 그 밖의 프롬프트(사용자 입력, `<pasted_content` 등)는 지금과 같다.
- 사용자가 relay 헤더를 직접 입력하면 집계만 유지되고 승인은 비워진다. 위조된 relay로 승인을 얻거나 연장하거나 복원할 수 없다.

### D2. TEMP 경로 분류 (P0-05 일부)
`IGNORED_PATH.search(p)`를 쓰는 세 곳을 `_ignored(state, p)`로 바꾼다.
1. 원래 경로와 `os.path.realpath(p)`(junction과 symlink 해석, 존재하지 않는 경로는 존재하는 상위까지 해석)를 **둘 다** 검사한다. 둘 중 하나라도 IGNORED_PATH에 걸리지 않으면 제외하지 않는다. 링크로 보호 대상을 우회하는 것을 막기 위해서다.
2. `.claude/(projects|plans|todos)`와 memory 분기는 지금처럼 제외한다.
3. `%TEMP%` 분기에만 걸린 경로는 실제 경로가 git 작업 트리 안이면 제외하지 않는다. git 작업 트리 판별은 `worktree.toplevel`을 쓰고, worktree의 `.git` 파일도 git이 직접 처리한다. 결과는 `state["dir_tops"]` 캐시를 재사용한다.
4. 결과:
   - A(일반 저장소)와 B(TEMP worktree)는 같은 정책을 받는다.
   - C(git이 아닌 TEMP 디렉터리)는 지금처럼 제외한다. 단 1번에 따라, 링크 대상이 보호 경로라면 제외하지 않는다.
   - 삭제된 worktree 경로는 존재하는 상위까지 올라가 판별한다. 그 상위가 git이 아니면 C로 분류된다.

### D3. 삭제된 추적 저장소 (R17, R18)
- `refresh_content`에서 `top` 디렉터리가 더 이상 없으면 그 저장소를 `content_removed`로 분류한다.
- Stop은 세션당 한 번만 "추적하던 저장소가 삭제됨 — 그 안의 변경은 검증 근거 없음(미확인)"이라고 알린다.
- 이후에는 `repos`와 `content`에서 제외한다. 검증 완료로 집계되는 일은 없다.
