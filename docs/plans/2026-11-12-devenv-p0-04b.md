## Context
P0-04b는 D3에서 세 번 연속 fix first로 끝났다. 원인은 완료 조건("어떤 경로로도 미검증 변경이 사라지지 않음")이 hook이 관측할 수 없는 영역(셸 내부 쓰기)에 걸려 있었기 때문이다(P0-S 계획 Context 1). 계약을 아래처럼 바꾸고, 남은 지적 F1~F3과 해제 경로(D3c)를 마감한다.

재정의한 D3 계약:
1. 기준선이 있는 저장소는 현재 내용 기준의 증거 없이 VERIFIED가 되지 않는다.
2. 사라진 저장소는 증명이 없으면 UNKNOWN(미확인)으로 남는다.
3. UNKNOWN은 명시적인 사용자 확인으로만 해제된다. 해제해도 VERIFIED가 되지 않는다.
4. 셸 내부 쓰기를 통제하는 일은 P0-07(최선 노력)과 OS 경계가 맡는다. 이 계획의 완료 조건이 아니다.

R1(relay 뒤 승인 유지)은 이 계획에서 뺀다. v2 운영 활성화 이후의 별도 항목이다. 기존 R1 테스트(승인이 사라지고 NOTE가 붙음)는 그대로 둔다.

## 현재 코드에서 확인한 사실 (main f34432c, `hooks/discipline.py`)
- `refresh_content`(1717행 이하)는 `repos_removed`의 경로가 `os.path.isdir`이면 `restore_repo`로 되살린다(1729-1730행). 그 경로가 git toplevel인지 확인하지 않는다. → F1
- `track_repo`(1570행 이하)는 `dir_tops` 캐시에 있는 값을 그대로 쓴다(1580-1581행). 저장소가 사라지거나 다른 저장소가 된 뒤에도 옛 toplevel을 돌려준다. → F1
- 사라진 저장소가 "정상 삭제"로 잊히는 조건은 `repo_state == clean`이고 `touched_tops`에 없을 때다(1739-1743행). `touched_tops`는 Stop마다 비운다(1829행). 백그라운드 셸은 Stop 뒤에도 계속 쓸 수 있으므로, 다음 Stop에서는 건드린 적 없는 저장소로 보인다. → F2
- `touched_tops`는 pre에서만 셸 대상을 기록한다(463-479행). post는 Edit/Write만 기록하고(552-565행), `on_fail`은 기록하지 않는다(1465-1468행). pre가 유실되거나(잠금 실패 등) fail 이벤트만 온 셸 명령은 기록이 없다. → F3
- 사라진 저장소(`content_removed`)와 reset 표식의 해석 불가 루트는 해제 경로가 없어서 Stop을 턴마다 한 번 막는다(1995-1999행, P0-S 개정 2·3의 위험 항목). 알려진 오탐 A-T9(셸로 지운 깨끗한 worktree)도 여기에 해당한다. → D3c
- 사용자 첫 줄 명령의 기존 패턴: `recover-state`는 `naming_text(prompt)`(778행)로 첫 줄을 뽑고, relay 형식과 마크업을 제외하며, 감사 기록을 `APPROVALS_HOME/state-recovery.jsonl`에 남긴다(2361-2379행, `recover_locked` 2473행).

## 설계 (최소 변경)

### D3a (F1): 되살릴 때 루트 확인, 캐시 정리
- `restore_repo`를 호출하기 전에 `worktree.toplevel(top)`이 `top`과 같은지(normcase) 확인한다. 같을 때만 되살린다.
  - 디렉터리는 있지만 git toplevel이 아니면(빈 폴더, 다른 저장소의 하위 폴더) 되살리지 않는다. `repos_removed`와 `content_removed`에 그대로 두어 미확인 보고가 유지된다.
  - git 조회가 예산 안에 끝나지 않으면(`worktree.budget_exhausted`) 되살리지 않고 이번 Stop에서는 그대로 둔다.
- `refresh_content`가 저장소를 `repos`에서 뺄 때, 그리고 `restore_repo`를 할 때, `dir_tops`에서 그 top을 가리키는 항목과 그 top 아래 경로의 항목을 지운다. 다음 조회는 git에 다시 묻는다.
- `track_repo`의 되살림(1594-1597행)도 같은 확인을 거친다. 이 경로에서는 방금 `worktree.toplevel`로 얻은 값이므로 캐시에서 온 값일 때만 다시 확인한다.

### D3b (F2, F3): 건드린 기록의 누락 메우기
- F2: 백그라운드로 넘어간 셸(`run_in_background` 또는 응답의 `backgroundTaskId`, 판별식은 `record_evidence` 1363-1365행의 것을 함수로 뽑아 재사용)이 대상으로 삼은 저장소와 그 시점의 추적 저장소 전부를 `background_tops`에 넣는다. 이 목록은 Stop에서 비우지 않는다(세션 동안 유지). 사라진 저장소의 "정상 삭제" 판정은 `touched_tops`와 `background_tops`를 함께 본다.
  - 해제: 그 저장소가 이후 Stop에서 내용 비교로 clean 판정을 받아도 목록에서 빼지 않는다. 백그라운드 작업이 언제 끝났는지 hook은 알 수 없기 때문이다(보수적, 계약 2). 사라지면 미확인으로 보고되고 D3c로만 해제된다.
- F3: 셸의 post와 fail에서도 pre와 같은 기록을 한다. `on_pre`의 셸 기록 부분(465-479행)을 `note_shell_touch(state, command, is_ps, cwd)`로 뽑아 `on_pre`, `on_post`(Bash/PowerShell 분기), `on_fail`에서 부른다. 이미 기록돼 있으면 변화가 없다(멱등).

### D3c: 사용자 확인으로 해제 `ack-missing <path>` (신규 기능)
- 트리거: UserPromptSubmit에서 `naming_text(prompt)`가 `ack-missing <path>` 형태일 때만(대소문자와 앞뒤 공백 무시, 경로는 따옴표 허용). relay 형식, 마크업 첫 줄, 둘째 줄 이하에서는 동작하지 않는다(`recover-state`와 같은 규칙).
- 대상: `<path>`를 절대 경로로 바꿔 normcase로 비교한다. 다음 두 목록에서 정확히 일치하는 항목만 해제한다. 접두사 일치나 와일드카드는 없다.
  - `content_removed`와 `repos_removed`의 사라진 저장소
  - 활성 `state_reset.roots` 가운데 게이트로 해제할 수 없는 루트(디렉터리가 없거나, 게이트 선언을 찾을 수 없는 루트)
- 해제하지 않는 것:
  - 현재 존재하고 게이트가 선언된 루트. 게이트 통과로만 해제된다(거부하고 그 사실을 안내).
  - 목록에 없는 경로(거부, 상태 불변).
- 효과: 해당 항목을 목록에서 지우고 `repo_state`의 그 top도 지운다. `acked_missing: [{path, at, prompt_id}]`에 기록한다(최근 50개). **evidence는 만들지 않고 어떤 루트도 passed로 표시하지 않는다.** 그 경로에 저장소가 다시 생기면 새 기준선으로 추적을 시작하고, 기준선은 `late`로 표시해 그 내용을 "변경 없음"으로 보지 않는다.
- 감사: `APPROVALS_HOME/state-recovery.jsonl`에 `kind: ack-missing` 줄을 추가한다(at, session, prompt_id, path, 해제한 목록 이름). 감사 기록에 실패하면 해제하지 않는다(`recover-state`와 같은 원칙).
- 안내: UserPromptSubmit additionalContext로 결과를 Claude에게 알린다("확인으로 해제됨, 검증된 것이 아니므로 보고에 '미확인'으로 남길 것" 또는 거부 사유). 출력은 ASCII 이스케이프를 쓴다(cp949 파이프 문제, P0-S 진행 기록).
- `REASON_REMOVED`와 reset 사유 문구에 `ack-missing <path>` 안내를 한 줄 더한다.
- 이 프롬프트의 나머지 처리(턴 증가, 재무장 등)는 평소대로 한다. `ack-missing`은 승인을 주지 않는다.

- 이 승인의 base는 main 루트(`C:/Users/user/.claude`)다. worktree 승인은 루트가 달라 재무장되지 않으므로(P0-S 개정 2), 이번에는 main 작업 트리에서 직접 개발한다.
